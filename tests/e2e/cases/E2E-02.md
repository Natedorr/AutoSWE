# E2E-02 — `waiting` on a question, resumed by a plain reply

| | |
|---|---|
| **Group** | questions |
| **Applies to** | every pass |
| **Scoped config** | none |
| **Run** | with the rest |

## The issue

**Title**

```
[E2E-02] Add a greeting helper - wording undecided
```

**Body**

```
Add `greet(name)` to `src/toolbox.py`. I have not decided whether it should return
"Hi, <name>" or "Hello, <name>" - ask me before you write the plan. Do not guess.
```

## The process

| # | openclaw posts | wait for | then check |
|---|---|---|---|
| 1 | `/plan` | `autoswe:waiting` | the question is its **own** comment, not folded into the sticky progress comment |
| 2 | `Use "Hello, <name>".` — plain text, **no slash command** | `autoswe:planned` | the reply alone resumed the task; the plan names "Hello" (soft) |
| 3 | `/fix` | `autoswe:fixed` | `greet()` returns `"Hello, ..."` |

## Status path

```
pending → planning → waiting → pending → planning → planned → pending → fixing → fixed
```

## Must never appear

`failed` · `error`

## Why this case exists

Two behaviours in one: the planner must stop and ask rather than guess, and a **plain-text
reply** on a `waiting` task must resume it with no command at all. Step 2 is the assertion —
if the task only moves when a slash command arrives, the question was pointless.

The standalone-comment check in step 1 matters more than it looks: a question folded into the
progress comment is a question the user never sees.

## Backend notes

The route to `waiting` differs. Claude and pi reach it through the MCP question tool; Codex
has no MCP, so it comes through the planner's text-parse fallback. The **state must be
identical** in every pass — only the route differs.
