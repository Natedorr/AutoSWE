# E2E-11 — Post-fix test gate red → `test_failed`

| | |
|---|---|
| **Group** | gates |
| **Applies to** | every pass, both providers |
| **Scoped config** | none — but needs the canary fixture from [`../SETUP.md`](../SETUP.md) |
| **Run** | with the rest |

## The issue

**Title**

```
[E2E-11] Set flag.txt to red
```

**Body**

```
Replace the contents of `flag.txt` with the word `red`. Do not touch anything under `tests/`.
```

`tests/test_canary.py` asserts the flag reads `green`, so the branch's suite goes red the
moment this change lands. That is the point.

## The process

| # | openclaw posts | wait for | then check |
|---|---|---|---|
| 1 | `/fix` | `autoswe:test_failed` | **the work was committed and pushed anyway** — the task branch has the change; the comment carries the test failure output |
| 2 | `/pr` | **no label change** across two wake-ups | refused while the gate is red; no PR opened |
| 3 | `/fix with set flag.txt back to green` | `autoswe:fixed` | the gate re-ran and passed |
| 4 | `/pr` | `autoswe:shipped` | the PR is open now that the gate is green |

## Status path

```
pending → fixing → test_failed → (/pr refused) → pending → fixing → fixed → pending → shipping → shipped
```

## Must never appear

`error`

## Why this case exists

Step 1 carries the assertion that matters: **a red gate must never lose the agent's work.**
The commit is pushed and the task rests at `test_failed` — a state that blocks shipping but
keeps everything. Discarding the branch on a red gate would be a serious regression and would
look, from the label alone, almost the same.

Step 3 additionally proves the task is not punished for the red gate: a restart from
`test_failed` gets a fresh attempt budget, the same way a restart from a review verdict does.
