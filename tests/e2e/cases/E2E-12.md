# E2E-12 — `failed` → `/retry` → the attempt guard

| | |
|---|---|
| **Group** | failure & guards |
| **Applies to** | every pass, both providers |
| **Scoped config** | `agent_timeout: 20` on the test project (or a dedicated throwaway project with it baked in) and `MAX_ATTEMPTS=3` |
| **Run** | **alone.** Every agent phase in the project times out while this is set. |

## The issue

**Title**

```
[E2E-12] Add a docstring to src/toolbox.py
```

**Body**

```
Add a module-level docstring to `src/toolbox.py` describing what the module is for.
```

An ordinary small change — it simply will never finish inside 20 seconds. The timeout is the
deterministic failure source; the change itself is irrelevant.

## The process

| # | openclaw posts | wait for | then check |
|---|---|---|---|
| 1 | `/plan` | `autoswe:failed` | the completion comment names a timeout |
| 2 | `/retry` | `autoswe:failed` | the replayed command was **`/plan`** — the last substantive command. `/retry` is never its own target |
| 3 | `/retry` | `autoswe:failed` | replayed again; a retry keeps resetting the attempt budget, so the guard has not fired yet |
| 4 | `/fix` | `autoswe:failed` | a new command from a failing state carries the attempt count **forward** rather than resetting it |
| 5 | `/fix` | `autoswe:failed` | one attempt further |
| 6 | `/fix` | `autoswe:failed` | **the guard fires**: a comment says the maximum attempts were reached, and **no agent ran at all** — the failure is immediate, not after another 20-second timeout |
| 7 | `/retry` | `autoswe:failed` | the limit-block *lets* `/retry` through: it is the one command that clears the guard — the budget is reset to `attempt_count = 1` and the last substantive command (`/fix`) **runs in full**, so the task returns to `autoswe:failed` after a timeout, not by an immediate refusal comment |

Step 6 is distinguishable from steps 1–5 by timing and comment: it arrives **immediately** and
says the limit was hit, rather than reporting a timeout. Step 7 is the mirror image — a **full**
20-second run, which is exactly what proves the guard was cleared. (Step 6 remains the explicit
pre-work refusal assertion; re-firing the guard from step 7's fresh budget would need two more
`/fix` cycles to re-saturate it, which this case deliberately does not run.)

## Status path

```
pending → planning → failed → pending → planning → failed → pending → planning → failed
        → pending → fixing → failed → pending → fixing → failed → failed
        → pending → fixing → failed
```

## Why this case exists

Three separate behaviours that only appear when things go wrong:

1. **`/retry` replays the last substantive command**, not itself — otherwise a retry after a
   failed `/plan` would do nothing at all.
2. **The attempt budget** resets on a retry but carries forward on a new command, so a task
   cannot be retried forever by alternating commands.
3. **The guard fires before the work** — immediately, with no agent run — and `/retry` is the
   single documented command that clears it: a fresh budget, and a replay of the last
   substantive command. `/fix`/`/plan` alone cannot restart a limit-blocked task, so the loop
   cannot be sustained without an explicit human retry. A task at its limit must stop costing
   money.

## Backend notes

The retry in step 2 is where the backends diverge:

| Pass | Expected |
|---|---|
| **A — Claude** | forks the checkpoint session, leaving the original intact |
| **B — Codex** | no session fork — resumes in place or starts fresh; the checkpoint is still written |
| **C — Mixed** (plan=codex, fix=claude) | step 4's `/fix` must **not** resume the checkpoint at all: it was written by a different backend, and the provenance check rejects it. **This is the reason pass C exists.** |
| **D — pi** | forks, like Claude |

The state sequence must be identical in all four. Only the session handling differs, and
confirming it needs the box's logs — ask the operator, or record the case as passed on states
with the session assertion unverified.

## Restore afterwards

Put `agent_timeout` back before running anything else, or every later case will time out.
