# E2E-09 — "Needs changes" → `/pr` refused → `/fix` → automatic re-review

| | |
|---|---|
| **Group** | review |
| **Applies to** | every pass, both providers |
| **Scoped config** | none |
| **Run** | with the rest. This is the highest-value case in the suite. |

## The issue

**Title**

```
[E2E-09] Add parse_port() - no tests please
```

**Body**

```
Add `parse_port(s)` to `src/toolbox.py` converting a string to an int port.
Do not add any test for it, and do not validate the range. I will add tests later.
```

An untested, unvalidated public helper is what the review prompt reliably calls out.

## The process

| # | openclaw posts | wait for | then check |
|---|---|---|---|
| 1 | `/fix` | `autoswe:fixed` | the helper is on the task branch, untested and unvalidated as asked |
| 2 | `/review` | `autoswe:review_failed` | the review comment says the verdict needs changes and notes that `/pr` is disabled |
| 3 | `/pr` | **no label change** across two wake-ups | the command was **refused**: a bot comment explains why, and no PR was opened |
| 4 | `/fix with add tests and validate the range 1-65535` | `autoswe:fixed`, then — **with no comment posted in between** — `autoswe:reviewing` and `autoswe:reviewed` | the re-review fired automatically; nothing openclaw or autoSWE posted triggered it |
| 5 | `/pr` | `autoswe:shipped` | the PR is open now that the review passes |

## Status path

```
fixed → reviewing → review_failed → (/pr refused, no state change)
      → fixing → fixed → [automatic] reviewing → reviewed → shipping → shipped
```

## Must never appear

`error`

## Why this case exists

Step 4 is the point of the case. A `/fix` that answers a failed review must trigger a
**re-review on its own** — the user should not have to remember to ask — and the task should
not be punished for the failed attempt by having its attempt budget eaten. Both are easy to
regress and neither shows up in the final label.

Step 3 is the second assertion: a refusal must be *visible*. A `/pr` that is silently dropped
and a `/pr` that is correctly refused look identical from the label alone.

Watch the comment stream closely between `fixed` and `reviewing` in step 4. A comment
appearing there means the re-review was triggered by something other than the flag.

## Soft assertions

The verdict class is model judgment. If step 2 lands on `review_blocked` instead, record it as
soft and carry on — the hard requirement is that `/pr` is refused in either state.
