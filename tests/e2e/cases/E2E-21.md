# E2E-21 — `/catchup` with a merge conflict the agent resolves

| | |
|---|---|
| **Group** | catchup |
| **Applies to** | every pass |
| **Scoped config** | none |
| **Run** | with the rest |

## Setup (before the issue is created)

`develop` must exist and must **disagree with `main` on one line** of `docs/notes.md`. openclaw
establishes this through the provider API, in this order:

1. Make sure `docs/notes.md` exists on `main` with a line `shared line: original`. Create or
   update it through the API if needed.
2. Make sure `develop` exists, then commit to `develop` a change to that same line:
   `shared line: changed on develop`.
3. Commit to `main` a change to the same line: `shared line: changed on main`.

Both branches now have an edit to the same line, so a merge of `main` into `develop` conflicts.

## The issue

This is a **control issue**. Its body is only the command.

**Title**

```
[E2E-21] Keep develop caught up with main (conflict)
```

**Body**

```
/catchup --from main --into develop
```

## The process

| # | openclaw does | wait for | then check |
|---|---|---|---|
| 1 | creates the control issue above | `autoswe:caught_up` | the agent resolved the conflict in `docs/notes.md`, the resolution keeps the intent of **both** edits (a line that says both changes, or a deliberate choice that names what it kept), and no conflict markers remain on the branch |
| 2 | — | — | a PR exists **into `develop`**, its body says to merge with a merge commit, and the PR is not closed by the control issue |
| 3 | — | — | the completion comment reports that a conflict file was resolved |

## Status path

```
pending → catching_up → caught_up
```

## Must never appear

`failed` · `error` · `synced` · `shipped`

## Why this case exists

A catch-up that conflicts is the path that cannot be done by plumbing alone, so it is the one
that calls Claude. Two things must hold. The agent must be given the **catch-up** prompt, which
names `main` and `develop` and says to preserve the downstream-only changes, with no plan text
and no resumed fix session. And the resolution must reach the PR, so a conflict that is resolved
locally but never pushed would show up here as `failed`, or as a PR that still conflicts.

The check on *which* intent the merge keeps is a judgment, so it is a soft assertion: a
resolution that keeps both edits, or one that clearly picks one and says so, passes. A silent
drop of the downstream edit fails.
