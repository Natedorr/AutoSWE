# autoSWE live E2E harness — START HERE

Everything for the live end-to-end suite lives in **this directory and nowhere else**.
If you are an agent (openclaw or otherwise) picking this up cold, read
[`MANIFEST.json`](MANIFEST.json) first — it is the machine-readable index, and every path in
it is stable.

The suite drives real issues on real repos through the autoSWE state machine against a real
coding backend. Each issue is a deliberately trivial code change; what is under test is the
**path through the state machine**, not the difficulty of the fix.

| File | Who uses it |
|------|-------------|
| [`MANIFEST.json`](MANIFEST.json) | any agent — index, roles, stable paths, upstream docs |
| [`PLAN.md`](PLAN.md) | humans — the spec: every issue, its state machine, its assertions |
| [`scenarios.json`](scenarios.json) | **openclaw** — the step list it executes |
| [`monitor.py`](monitor.py) | **autoSWE box**, on cron — scores `data/queue.json`, writes `report.json` |
| [`seed_testbed.sh`](seed_testbed.sh) | operator — creates the two fixture repos |
| `observed.json` / `report.json` | generated by `monitor.py`; gitignored; cleared with `--reset` |

## Running a pass

```bash
# 1. testbed (once)
e2e/seed_testbed.sh <owner>
#    then wire config/repos.json + the "repos" block in e2e/scenarios.json

# 2. pick the backend pass in config/harnesses.json + repos.json
#    A = claude everywhere, B = codex everywhere, C = plan:codex + fix/review:claude

# 3. start clean
python e2e/monitor.py --reset

# 4. cron  (monitor faster than the poller — see Scoring)
#    */5 * * * * cd /opt/autoswe && ./poller.sh
#    *   * * * * cd /opt/autoswe && .venv/bin/python e2e/monitor.py --write-report --pass-label A-claude --quiet

# 5. openclaw opens the issues and drives e2e/scenarios.json

# 6. read the board any time
python e2e/monitor.py --pass-label A-claude
```

`monitor.py` exits 1 when anything is `fail` or `stalled`, so cron mail or a CI step can gate
on it without parsing the report.

## The contract between the two sides

openclaw and the monitor never talk to each other. They agree on exactly one thing: **the
issue title starts with the scenario id in brackets** — `[E2E-09] ...`. That marker is how
`monitor.py` maps a queue entry back to a scenario, so openclaw must not alter the titles in
`scenarios.json`.

openclaw watches `autoswe:*` **labels** — the only state visible from outside. The monitor
watches `autoswe_status` in `data/queue.json` — the actual source of truth. Any divergence
between the two is itself a bug worth reporting: the label mirror is supposed to be faithful.

## Scoring

`monitor.py` checks the observed status *sequence*, not just the final state: reaching `fixed`
by the wrong route fails. Verdicts are `pass`, `fail`, `stalled`, `in_progress`,
`not_started`, `soft_fail` (model-judgment assertions — E2E-10's verdict class, E2E-19's
guidance — need a human read).

Only **resting** states are load-bearing. `pending` and the RUNNING states are transient — the
poller syncs and dispatches in one run, so a short phase can begin and end between two samples
— which is why the monitor is scheduled every minute against a 5-minute poller, and why the
matcher never *requires* them. They are still recorded when caught, and still trip
`forbidden_statuses`. Repeat visits to one status are kept distinct by
`(status, attempt_count, last_dispatched_command_id)`, without which E2E-12's seven
consecutive `failed` states would collapse into one.

Assertions needing the provider API or the git tree (commit trailers, PR base branch, "no
comment between `fixed` and `reviewing`") are listed per step in `scenarios.json` and are
openclaw's to check. The monitor scores what the queue can prove on its own; between the two,
every assertion in `PLAN.md` §3 has an owner.

## What this tests, and what tests it

This is the live layer on top of the offline suite in [`../docs/autoswe/testing.md`](../docs/autoswe/testing.md).
Offline proves the state machine against fakes; this proves the same machine against a real
provider and a real backend. When a live scenario finds a bug, the fix belongs in **both**
places — add the transition row offline (`tests/scenarios/transitions.py`) *and* keep the
scenario here. See `PLAN.md` §4 for what is deliberately out of scope.
